go-workflow is a Go implementation of the
[Workflow SDK](https://workflow-sdk.dev). It follows the SDK's behavior and
stores the same data, so the Workflow SDK's tools, like its web UI, can read Go
runs.

You write a workflow as an ordinary Go function. The work it does with side
effects goes into **steps**, and every step's result is recorded. If the process
crashes, restarts, or is redeployed in the middle of a run, the run is delivered
again, the function replays from the beginning, and recorded steps return their
recorded results instead of running again. The run resumes where it left off.

## Core ideas

| Concept | What it is |
| --- | --- |
| **Workflow** | A struct type that embeds `workflow.Struct[Out]` to declare its output type. Its package path and type name are the workflow name, and a value of it is the input of a run. |
| **Runner** | A function that takes a context and the workflow input, returns the output and an error, and executes the workflow. You register it with `workflow.Use`. |
| **Step** | A function with the same shape as a runner that does the real work and side effects. It runs at least once and retries on error. |
| **Run** | One execution of a workflow, recorded as an append-only event log. |
| **World** | The backend that stores runs, queues deliveries, and holds streams: Vercel, AWS, Postgres, a local SQLite file, or your own. |
| **Client** | The API that code outside a run uses to start, read, cancel, and resume runs. |

## Two contexts

A run executes in one of two contexts.

- In **workflow context**, the runner's own code executes as a *flow*. The flow
  replays the runner from the beginning, records the operations it starts
  (steps, timers, hooks, webhooks, and child runs), queues the steps it needs,
  and records the run's result once the runner returns.
- In **step context**, a step function executes as a *step*. The step delivery
  replays the runner up to that step and calls the step function.

Because the runner replays on every delivery, it must be **deterministic**: it
does side effects only through steps and reads time only through
`workflow.Now`. The [analyzer](/docs/tooling/analyzer) reports common ways runners
break these rules. [How Replay Works](/docs/replay) explains the model in detail.

## What you get

- **Steps** with automatic retries, fatal and delayed-retry errors, and stable
  idempotency keys.
- [Concurrent work](/docs/concurrency) that can wait for a group or race
  competing operations.
- [Durable waits](/docs/sleep) that hold no process, even for days or weeks.
- [Cancellation](/docs/cancellation) to stop work manually or set a timeout.
- **Hooks and webhooks** that suspend a run until an external event or HTTP
  request resumes it with a typed payload.
- **Streams** of bytes that steps or outside code write and readers consume
  while the run is still going.
- **Rollbacks**: compensations that run in registration order when a run fails,
  so deferred ones run in reverse.
- **Typed errors** that survive replay, so `errors.Is` and `errors.As` work on a
  failed step or run.
- **Child runs** and direct composition of runners.
- **Worlds** for Vercel, AWS, PostgreSQL, and local development, plus an
  in-memory World for tests and a conformance suite for your own.
- **Tooling**: a vet analyzer, a [go-dev](https://github.com/eriicafes/go-dev)
  integration, and compatibility with the Workflow SDK web UI.

## Packages

| Package | Purpose |
| --- | --- |
| [`workflow`](/docs/reference/workflow) | The API runners, steps, and applications use. |
| [`worlds`](/docs/reference/worlds) | The World contract, the runtime, the client, and the HTTP server. |
| [`worlds/vercel`](/docs/worlds/vercel) | Vercel workflow storage, Vercel Queues. |
| [`worlds/aws`](/docs/worlds/aws) | DynamoDB, SQS, optional EventBridge Scheduler. |
| [`worlds/postgres`](/docs/worlds/postgres) | PostgreSQL with LISTEN/NOTIFY workers. |
| [`worlds/local`](/docs/worlds/local) | A SQLite file on disk, in-process delivery. |
| [`worlds/testworld`](/docs/worlds/testworld) | In-memory World for tests. |
| [`workflowtest`](/docs/worlds/custom#conformance) | Conformance suites for World implementations. |
| [`check`](/docs/tooling/analyzer) and `cmd/workflowcheck` | Static analyzer and its vet tool. |
| [`workflowdev`](/docs/tooling/dev) | go-dev integration. |
| [`go-workflow/world-http`](/docs/tooling/world-http) | JavaScript World adapter the Workflow SDK web UI loads. |
