## Errors that survive replay

A failed step's error is recorded in the event log and read back on every
replay. Go errors are values with types, so go-workflow records more than the
message: it keeps the **type, message, and JSON encoding of every error in the
original chain**.

`workflow.Step` returns a failed step's error as a `*workflow.Error`, and
`Run.Value` returns a failed run's error as a `*workflow.RunFailedError`
whose cause is the run's `*workflow.Error`. Because the chain is preserved,
`errors.Is` and `errors.As` keep working after replay and across child runs.

```go
var ErrCardDeclined = errors.New("card declined")

type LimitError struct{ Limit int }

func (e *LimitError) Error() string { return fmt.Sprintf("over limit %d", e.Limit) }
```

```go
_, err := workflow.Step(ctx, charge, order)
var limit *LimitError
switch {
case errors.Is(err, ErrCardDeclined):
	// ...
case errors.As(err, &limit):
	// limit.Limit is decoded from the recorded error.
}
```

How matching works:

- `errors.Is` matches a target with the **same type and message** as an error
  in the recorded chain. That is how sentinel errors made with `errors.New`
  match.
- `errors.As` matches a target whose **type** is the type of an error in the
  chain and decodes that error's **exported fields** from JSON into it. Give
  error types exported fields for anything callers need.

`worlds.NewError(err)` builds an `*Error` from any error, and
`worlds.DecodeError(data)` decodes the JSON stored in a run's or step's
`Error` field.

`worlds.FatalError` and `worlds.RetryableError` are plain Go error wrappers.
Durable steps inspect them before encoding the result and record the retry
time separately. `worlds.Error` records them in its chain like other errors, so `errors.As`
still matches them after replay and rebuilds their `Cause` from the rest of
the recorded chain.

## Step retries

A failed step gets three retries after its first attempt by default. Set
`StepOptions.MaxRetries` to change the limit:

```go
receipt, err := workflow.Step(ctx, chargeCard, order, workflow.StepOptions{
	MaxRetries: 10,
})
if err != nil {
	return Result{}, err
}
```

Omitting options allows three retries. Passing `StepOptions{}` allows none.
If multiple options are passed, the last one applies.

While a retry is scheduled, the step's status is `pending` and `RetryAfter`
holds the earliest time of the next attempt, one second after the failure
unless the error names a delay. A step's queue message lives for seven days,
so a retry that would be due after it expires fails the step instead.
[Inline steps](/docs/inline-steps#retrying-failures) use the same policy.

When retries run out, the step fails with a fatal error that says so and
keeps the last attempt's error as its cause:

```text
Step "example.com/shop.chargeCard" failed after 3 retries: card declined
```

`errors.Is` and `errors.As` still reach the last error through it, so a
runner matches its own errors the same way whether a step failed at once or
after its retries:

```go
_, err := workflow.Step(ctx, chargeCard, order)
if errors.Is(err, ErrCardDeclined) {
	// ...
}
```

An error wrapped in `FatalError` is recorded as it is, with no such message.
A step whose attempts all started and whose last one never recorded a result,
because its delivery crashed or was stopped, fails with
`Step "..." exceeded max retries (3 retries): attempt 4 started at ... and
never recorded a result`, which has no cause.

| Return from a step | Effect |
| --- | --- |
| `nil` error | Step completes. |
| Any other error | Retried after a second while retries remain, then fails. |
| `workflow.FatalError(err)` | Fails immediately, never retried. |
| Another fatal error | Fails immediately, never retried. See below. |
| `workflow.RetryableError(err, after)` | Retried no sooner than `after`, or a second when `after` is zero, while retries remain. |

Some errors are fatal without `FatalError`, because retrying cannot change
them: a `*workflow.SerializationError`, the `*workflow.RunFailedError` and
`*workflow.RunCancelledError` that `Run.Value` returns for a failed or
cancelled run, and the `*workflow.EncryptionKeyLookupError` of a run whose
encryption key cannot be resolved for good. An error type of your own is
fatal when it has a `Fatal() bool` method that returns true.
`workflow.IsFatal(err)` reports whether a step failing with `err` is retried.

<Callout type="info" title="Steps only">
`FatalError` and `RetryableError` only change how a step is retried, so return
them from step functions, [inline steps](/docs/inline-steps), and
[rollback](/docs/rollbacks) compensations. Runs are never retried: a runner
that returns an error fails its run whether or not the error is wrapped.
</Callout>

Both wrappers return `nil` when `err` is `nil`, so you can wrap
unconditionally.

```go
func sendInvoice(ctx context.Context, invoice Invoice) (struct{}, error) {
	err := mailer.Send(ctx, invoice)
	if errors.Is(err, mailer.ErrInvalidAddress) {
		return struct{}{}, workflow.FatalError(err)
	}

	return struct{}{}, err
}
```

## Failing a run

A runner fails its run by returning an error or panicking. Runs are not
retried, so there is no need to wrap a runner's error in `FatalError`. Error panics preserve
the original error; other panic values become `workflow: panic: <value>` errors.
Before the run is marked failed, deferred [rollbacks](/docs/rollbacks) run in
Go's defer order, with the last defer first. The run's error
is recorded as a `*workflow.Error`, and `Run.Value` returns it as the cause
of a `*workflow.RunFailedError`, which also holds the run's ID and error
code, so callers can inspect it with `errors.Is` and `errors.As`:

```go
_, err := run.Value(ctx)
if errors.Is(err, ErrCardDeclined) {
	// ...
}
```

A runner may also handle a step's error and keep going, for example by
retrying with different input or taking another branch.

### Failures the runtime records

The runtime fails a run itself in a few cases. Each `run_failed` event
carries an error code in plain text, which `worlds.RunFailedErrorCode` reads
and tools use to sort failures:

| Error code | The run failed because | Matches |
| --- | --- | --- |
| `USER_ERROR` | The runner returned an error or panicked. | The runner's error |
| `WORKFLOW_NOT_REGISTERED` | The worker has no runner for the run's workflow. | `worlds.ErrWorkflowNotRegistered` |
| `CORRUPTED_EVENT_LOG` | Its replay kept [diverging](/docs/replay#replay-divergence) from its event log. | `worlds.ErrCorruptedEventLog` |
| `DEPLOYMENT_MISMATCH` | Its deliveries kept reaching a deployment other than the one it is [pinned to](/docs/replay#pinning-runs-to-a-deployment). | `worlds.ErrDeploymentMismatch` |
| `MAX_DELIVERIES_EXCEEDED` | One message of its flow was delivered more than 48 times without the delivery succeeding. | `worlds.ErrMaxDeliveriesExceeded` |
| `MAX_EVENTS_EXCEEDED` | Its event log reached the most events a run may hold. | `worlds.ErrMaxEventsExceeded` |
| `REPLAY_TIMEOUT` | Replaying it kept taking longer than a delivery may replay for. | `worlds.ErrReplayTimeout` |
| `RUNTIME_ERROR` | The runtime could not set up its replay at all, such as for a run ID it cannot read. | |

None of these run the run's [rollbacks](/docs/rollbacks), except a runner's
own failure.

A run may hold 25,000 events. A flow checks the count before it replays and
each time a step it ran inline records its result, and fails a run at the
limit, so split long-running work into [child runs](/docs/composition) well
before it. `WORKFLOW_MAX_EVENTS` sets another limit where the World sets none
for the run, and `WORKFLOW_MAX_EVENTS_OVERRIDE` lowers whichever applies. The
runtime logs a warning when a run reaches half, 80% and 95% of its limit.

A flow delivery may spend 240 seconds replaying: reading the log, running the
runner between steps, and writing events. The time its inline steps'
functions run and the time it waits for other work do not count. A delivery
that passes the limit fails, so the queue delivers its message again, and the
fourth delivery of a message to pass it fails the run.
`WORKFLOW_REPLAY_TIMEOUT_MS` sets the limit, between 30,000 and 780,000, and
`WORKFLOW_REPLAY_TIMEOUT_MAX_RETRIES` how many deliveries are retried. A
World that does not count a message's deliveries retries without failing the
run.

A step's message is delivered again on purpose while the step retries, so
the limit of 48 deliveries does not fail a step by itself. Past it, a step
that no delivery has started, retried, or scheduled for an hour fails with
`Step "..." failed with MAX_DELIVERIES_EXCEEDED`, an error matching
`worlds.ErrMaxDeliveriesExceeded` that the runner can handle like any step
failure.

A step whose arguments or return value cannot be encoded fails without
retrying with a `*workflow.SerializationError`, whose message is
`Failed to serialize step arguments` or `Failed to serialize step return
value` followed by the encoding error. It is recorded as an Error named
`SerializationError`, as the Workflow SDK records it. A step function's
failure to decode its input, and a payload that fails to decrypt, reach the
runner as ordinary errors. The runner can handle any of them, and a run that
returns one fails with `USER_ERROR`.

## Returned errors

Match a variable with `errors.Is`, and a `*...Error` type with `errors.As`,
which also reads its fields.

| Error | Returned when |
| --- | --- |
| `workflow.ErrNoClient` | A function that needs a Client, such as `Start`, is called with no Client in the context and outside a run. |
| `workflow.ErrNoWorkflow` | A workflow-context function such as `Step` is called outside workflow context (including in step context), a hook created outside workflow context is used, or a stream function is called outside a run. |
| `workflow.ErrNotInStep` | A function that does I/O, such as `Writer` or `Run.Reader`, is called in workflow context. |
| `*workflow.RunFailedError` | `Run.Value` on a failed run. Its `Cause` is the run's error, and `ErrorCode` its [error code](#failures-the-runtime-records). It is fatal, so a step awaiting the run is not retried. |
| `*workflow.RunCancelledError` | `Run.Value` on a cancelled run. It matches `workflow.ErrRunCancelled`, and is fatal. Running steps keep their contexts unless they use an explicitly cancelled context. |
| `*workflow.SerializationError` | A step whose arguments or return value cannot be encoded. It is fatal. |
| `*workflow.EncryptionKeyLookupError` | `Run.Writer` when the run's encryption key cannot be resolved for good, such as for a run that does not exist. It is fatal; a transient failure is returned as it is. |
| `workflow.ErrResumeNotQueued` | `ResumeHook` recorded the payload but could not queue its run. Don't resend the payload. |
| `workflow.ErrNilResult` | A nil `*Result` is returned from a `Then` callback or awaited. |
| `*workflow.HookNotFoundError` | Resuming a token that no active hook has. |
| `workflow.ErrHookNotRegistered` | Receiving or selecting a hook from another execution or a lookup. |
| `*workflow.HookConflictError` | Receiving or selecting a hook whose token another active hook already has. The token is claimed on first use, not at creation. |
| `*workflow.HookForceClaimedError` | Receiving from a hook whose token another run took over with `HookOption.Force`. |
| `*workflow.StartError` | `Start` with `StartOptions.Hook` could not confirm that the World admitted the run (`Stage` is `admission`) or queued its first delivery (`queue`), after sending again three times. The run may exist and run. Starting again with the same token is safe: it starts no second run while the first holds the token. It wraps `worlds.ErrStartHookDisabled` when the World's start hook admission is switched off. |
| `worlds.ErrCorruptedEventLog` | `Run.Value` on a run whose replay kept diverging from its event log. See [Replay divergence](/docs/replay#replay-divergence). |
| `worlds.ErrMaxEventsExceeded`, `worlds.ErrReplayTimeout`, `worlds.ErrMaxDeliveriesExceeded` | `Run.Value` on a run the runtime failed for a limit. See [Failures the runtime records](#failures-the-runtime-records). |

The [`worlds` reference](/docs/reference/worlds#errors) lists the errors Worlds
return, such as `ErrRunNotFound` and `ErrHookNotActive`.
